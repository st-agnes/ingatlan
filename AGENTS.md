# Working in this repository

This is Otthonra, a Hungarian real-estate matching application. The backend is .NET 8 with EF Core/Pomelo and MySQL 8. The browser frontend is buildless native JavaScript/CSS in `dist/`; no npm install or frontend compilation is needed.

## Prepare and run

- The `.devcontainer/` configuration supplies the .NET SDK, Node.js 22, and MySQL, then runs the setup/start commands automatically.
- In another supported development environment, run `bash scripts/cloud-setup.sh`. It installs a missing SDK into ignored `.local/dotnet`, restores, builds, and checks the project.
- The development web port is configured once by `scripts/development-config.mjs` (default 3000); listener, readiness and forwarded URLs must agree. Full Docker Compose keeps its separate web port 8080.
- Use `node scripts/dev.mjs --restart` to wait for a complete stop and start. Start/stop commands serialize through a local lock; postStart and postAttach may call them together. Keep owned API/web process groups independent and restart failed children without taking the web down on API failure. Status is read-only: `node scripts/dev.mjs --status`.
- Start services with `node scripts/dev.mjs --background`; logs are in `.local/dev.log`. Stop the supervisor with `node scripts/dev.mjs --stop`.
- `ConnectionStrings__MySql` selects a supplied database. Without it, the development supervisor starts the root Compose MySQL service.
- The web UI is on port 3000 and proxies `/api` to .NET. Use the forwarded web origin when connecting from a phone or remote browser.
- The backend Docker build context is the repository root (`docker build -f backend/Dockerfile .`), because it embeds `dist/data/settlements.json` shared with the browser.
- With `Database__Initialize=true`, startup runs `EnsureCreated` and then the additive, repeatable `SchemaUpgrade` version `20261102-locations-and-lot-area`. Existing rows use canonical legacy-location fallback; do not delete the database or Docker volume to apply this upgrade. This is a targeted upgrade, not a general EF migration system. The separately enabled hosted TEST fixture reset described below is an intentional deployment operation, not part of the additive schema upgrade.
- In a managed cloud, use its provided network/proxy/CA and Docker instructions. Diagnose denied operations or service errors rather than disabling sandboxing, TLS verification, or credential protections.

## Business and data rules

- Creating a search must confirm the saved entity and offer discovery. Activate its saved ID only when the user chooses discovery; await activation before navigation. Dismissal preserves the previous active entity. Editing does not reopen the creation prompt.
- Location suggestions must not obscure their input. Outside pointer/focus closes suggestions without selecting or erasing text; clean up per-editor document listeners when the modal closes or is replaced.
- An account can own multiple properties and searches. Every action checks ownership and the active entity.
- Recommendations use hard canonical location/type, ownership, archive and account-type gates. Exact matches (100) are exhausted before partial matches; partial discovery requires per-active-profile explicit consent, and partial decisions require AllowApproximate plus server verification that no unseen exact pair remains. Already judged pairs stay excluded for that side. Rules.Compatible means exact criteria satisfaction.
- A property selects one canonical `locationId`; a search selects a nonempty `locationIds` array. Public `GET /api/locations?q=&limit=` returns `{items:[{id,label,city,district}]}`. Explicit unknown IDs must fail validation. Keep legacy city/district reads compatible only with known catalogue values.
- Search locations use OR semantics across towns and Budapest districts. `city:Budapest` covers all districts; `district:Budapest:5` covers only district V. All other search filters still apply.
- Search-only city areas use stable `area:<center>` IDs, stored as one choice in `locationIds` (no expansion against the 50-choice cap). `dist/data/agglomerations.json` and generated `dist/agglomerations-data.js` contain the same KSH public-registry membership; counts include the center once, Budapest all districts but one settlement. Exact property locations must reject areas in UI, local model, API adapter and backend. Search kind defaults to `search`; `kind=property` hides groups. Keep legacy town resolution restricted to real cities/districts. Source attribution must remain visible near the search picker, and KSH CC BY 4.0 provenance in notices/docs. `scripts/import-agglomerations.py` regenerates and checks the pinned source offline.
- Preserve nullable search bounds through form, storage and API serialization. In particular, blank `minPrice`, `maxArea` and `maxRooms` remain `null` and mean unbounded; do not coerce them to zero or a synthetic upper bound.
- `lotArea` is required and positive on every `Ház` save (max 10,000,000 m²); clear it for other property types. House save clears floor/balcony/elevator; house searches clear floors/balcony/elevator and ignore any old irrelevant restrictions. There are no search plot-area bounds.
- `dist/data/settlements.json` is the canonical shared municipality source, embedded by .NET; `dist/locations-data.js` is its generated browser module. Source, license and update instructions are in `docs/LOCATION-DATA.md`. Preserve existing demo storage key `otthonra.demo.v3`, IDs, decisions, matches and balances when upgrading records.
- Optional attribute selections are OR within buildings/constructionAges/views/floors, AND across criteria for exact matching. Conditions are ordinal: at least the lowest acceptable selected condition is exact. Empty lists/ceiling height do not constrain; unknown seller data incurs a full loss on a specified criterion. Floor11 means actual floors>=11; preserve legacy actual floor values and distinguish unknown from0. Partial match penalties follow the documented weights/deviation ratios.
- Property `insulated`, `airConditioning`, `solarPanels` are nullable booleans: preserve false versus unknown in UI, local storage and API. `energyRating` remains optional public text. `heatingType` and `secondaryHeatingType` are optional choices from the shared heating list, including explicit no heating; search `heatingTypes` is optional OR over PRIMARY heating only. `parkingTypes` is an optional multiselect; keep `parkingType` as a compatibility string and preserve old prose as one value, never split it. Unknown legacy primary heating/parking may be retained unchanged, but new unknown values are invalid. Legacy conditions normalize on read/match; retain unchanged unknown legacy metadata on update while rejecting newly introduced unknown enum values.
- `20261105-property-attributes` adds the optional columns with the existing schema lock, preserving the old location upgrade. CI simulates the original schema with `backend/fixtures/previous-schema.sql` only in its disposable database, then checks attribute round trips and restart preservation with `backend/attributes-smoke.mjs`. Do not run the destructive CI SQL fixture against a deployed database. Shipping this feature requires a new API image; an old digest does not implement these filters.
- Store nullable `wholeRooms`/`halfRooms` separately to preserve exact room composition; weighted `rooms = wholeRooms + halfRooms/2` is used for matching. Old total-only requests still work; unchanged totals preserve saved composition, exact half-step legacy totals derive display counts without row rewrites, other old decimals never round silently.
- `20261106-seller-form-details` adds room-count columns, secondary heating, parking JSON and search heating JSON under the same schema lock. Keep this upgrade additive. `backend/seller-form-smoke.mjs` checks actual API persistence and restart; `tests/seller-form-browser.test.mjs` checks all three viewports. All positive/nonnegative number inputs prevent negative typing/paste/mobile input without adding negative-warning copy. Keep decimal typing and optional blank bounds usable; the basement category remains valid.
- Account types are `private` and `agent`, selected at registration and immutable through ordinary profile updates. Missing legacy types default to `private`. Derive all public `ownerAccountType` values from the owner user, never listing/search input or current viewer. Hide all account-type badges on the current user’s own entities/workspace; show explicit Magánszemély/Ingatlanközvetítő on foreign discovery and incoming-like entities. The full profile type may remain in settings. Keep contacts private until a match. Ship shared `dist/accounts.js` in the Hosting allowlist.
- `canInteract` is symmetric: agent–agent is forbidden in both discovery roles, incoming likes and direct new/replayed decisions (HTTP 400, no debit/new decision). Filter before feed/pagination limits using actual owner types. Private actors can see both types. Preserve historical matches/messages and saved history; the new rule does not erase old conversations.
- Search-side likes cost zero for private accounts and one credit for agents; property-side likes cost two credits for both account types. Passes are free. Read the actor type from the locked database user. Credit balance, ledger, decision, and match updates remain transactional; retries debit no additional credits and insufficient funds create no decision/ledger/match.
- `POST /reports` accepts a source property/search ID and one reason: `suspected_agent` (Ingatlanközvetítő; private owner only), `misleading_content` (Hamis, megtévesztő tartalom), `other_violation` (Egyéb szabálytalanság) or `no_longer_current` (Már nem aktuális). The latter three apply to any other live owner type; self/nonexistent/archived sources remain forbidden. Derive the owner server-side. Omitted/null reason keeps legacy suspected_agent behavior; explicit empty/unknown is 400. The universal foreign-entity report button says Hirdetés jelentése and remains available for another reason.
- Reports deduplicate on `(ReporterId,EntityKind,EntityId,Reason)`, not owner. A different ad or reason is distinct; repeat/concurrent same context returns the original receipt and original UTC CreatedAt. Never render or return report timestamps. `/me/entities` adds reporter-private `reportedEntities:[{entityKind,entityId,reason}]`; keep `reportedOwnerIds` only for compatibility and never use it to disable unrelated ads/reasons. Do not expose other reporters, counts or report details. Reports do not automatically change account type, credits or visibility.
- `20261107-interactions-and-report-reasons` replaces only the old report unique index under the existing schema lock. Preserve old report IDs/reasons/timestamps; make both index upgrade and version marker idempotent. Keep prior schema upgrades.
- `/incoming-likes?offset=0&limit=50` is authenticated and scoped exclusively to the current owned active entity; no arbitrary target entity ID. Return `{active,items,total,offset,limit,hasMore,likeCost}`, ordered by likedAt/decision ID descending, with public feed pair data and `likedAt`, `myDecision:null|liked|passed`, `matchId`, `compatible`. Exclude archived/self/agent–agent counterparties; include prior own decisions, matches and currently incompatible pairs with actions disabled as appropriate. View is free; replies go through normal transactional `/decisions` pricing. Keep public property DTO own=false and no contacts/exact address.
- The separate Kedveltek page follows active profile changes, pages the entire list, and guards against late responses from another active profile. Show matched/returned/passed/incompatible states. Pair-specific actions must not accidentally operate on feed[0]; preserve the ordinary affordability, ownership, busy and match-contact rules. No active profile yields an empty page. Invalid offset/limit values return 400 (offset0..1000000, limit1..100).
- `20261107-account-types-and-reports` adds `Users.AccountType` and creates `UserReports` under the existing schema lock, including old EnsureCreated databases. Keep old rows/credits/IDs during the normal schema upgrade; the separately authorized hosted-test fixture reset has its own lifecycle. The destructive CI-only previous-schema fixture drops this table/column/version solely in the disposable CI database; never execute it against a deployed database.
- Public cards contain no contact details or exact address. Only a reciprocal match permits contact access and messaging.
- Keep runtime EF Core packages on the same patch version; Design is private but runtime references must flow to test/client projects.
- Large public text and JSON map to MySQL longtext with explicit input size limits.
- `.env`, `.local`, build output, logs, and credentials are excluded from version control. Use `scripts/setup-local.mjs` to generate local secrets without printing them.
- Stripe values are server-side configuration. Credit only verified paid webhook events, idempotently; the checkout return URL must never grant credits.

## Weighted recommendation ranking

- Keep backend MatchingRanking and browser matching.js semantics aligned with regression tests. Locations and property type are hard gates; all requested numeric/attribute criteria influence exactness and weighted partial score. Every exact pair is100; a nonexact pair must never round up to100. Houses ignore floor/lift/balcony criteria.
- Buyer recommendations sort by score, prior incoming like, then value for money. Seller recommendations sort by incoming like, score, then search specificity. Exact and approximate discovery are separate server phases; a prior like cannot pull a partial candidate ahead of remaining exact candidates. Keep stable ID tiebreaks.
- Value for money gives primary weight to living area per price, caps the house plot contribution at20% of living area, and bounds optional attribute bonuses. Specificity is an independent0–100 metric of search narrowness; do not confuse either metric with compatibility.
- Keep recommendation SQL prefilters, lean projections, bounded top50 retention and full DTO loading only for final candidates. Reuse prepared search criteria; avoid N+1 owner/like lookups and unbounded full listing materialization. Do not prematurely limit before exact/partial selection. Preserve additive schema/index upgrades.
- Discovery asks for lower matches before showing the first partial card. Scope consent to the active entity and its current criteria; reset after switching/editing/logging out and guard late responses. Partial incoming-like replies use the same explicit consent/decision gate. Public cards retain contact privacy and valid0% display. matchDetails retains concrete requested/actual values with matches flags in the API, while the UI omits hard location/type criteria, uses short labels for successes and shows only the other party value for a mismatch (property candidate: actual; search candidate: expected). Never repeat the active entity’s own criterion value in comparison rows. Keep C#/JS semantics aligned and skip formatting during lean scans. Display specificity as a percentage. The consent gate has one affirmative button; doing nothing leaves partial cards hidden.

- Public marketing states concrete audience benefits: sellers see real demand, reach potential buyers and receive interest from specific searchers without exposing contacts before a match; buyers publish precise needs with contact control and avoid repeat ads within the same active search. Keep the hero compact and the full audience benefit lists below previews so both card groups remain visible in the first viewport.

## Seller insights and prepaid rejection feedback

- Owner-only GET /properties/{id}/insights exposes unique actual viewers (PropertyImpressions unique PropertyId+ViewerUserId), distinct search-side people who liked, property-side liked search count, and distinct viewed people with a mutual match divided by unique viewers. Never count a feed fetch or all50 returned candidates as impressions. Only the actually visible foreign property card in an owned active search calls POST /impressions. Historical views are not invented. Read related counts from one snapshot; preserve ownership/archive/self/agent gates.
- Feedback packages cost10/20/50credits upfront for10/20/50 accepted responses, last14UTCdays and never overlap on a property. Reaching quota early stops prompts but retains the original period until expiry; another package may be bought after expiry. New purchases on archived properties are forbidden; old statistics/history remain accessible. Purchase RequestId is an owner-scoped unique GUID, receipts survive expiry, and retry never charges twice. Pause/resume controls new invitations, not the deadline or already issued responses.
- New search-side passes increment a bounded persistent per-user FeedbackPassCounter. At20, an eligible enabled campaign may issue a prompt and reset it. Never increment on a replay, like or seller decision. Keep one unexpired pending invitation per user and unique PackageId+BuyerId across all outcomes/profile switches. Each invitation reserves one remaining slot for15minutes at most, bounded by the campaign deadline. Property/package locks serialize reservations and answers; received responses plus live reservations never exceed package size.
- Feedback is one of eight fixed reason buttons. decline means Nem szeretnék válaszolni and never increments received count or produces a paid response. Other is a category, not unrestricted text. Buyer authorization, immutable first answer, idempotent same-answer retry, post-lock expiry checks and consistent user->property->package lock order are required. Late expired answers cannot consume refunded credits. Seller response history/aggregates contain reason and timestamp only, never buyer identity/search/contact details.
- Pending prompts persist across reloads and block the next property card/impression until one response is submitted or the request expires. Each button submits directly and closes after acknowledgement; Escape means decline, failures retain a retryable prompt. Use safe public first names with Hungarian dative title, neutral fallback when unavailable. Keep keyboard/touch and all8options usable on mobile.
- FeedbackRefundService reuses the existing hourly Scheduler/worker/read catch-up through LikeRefundService. At expiry, refund exactly Size-ReceivedCount once, with independent unique CreditEntry charge/refund keys and one package-linked private notification. UserNotifications.DecisionId is nullable for package refunds; preserve original decision links and keys. Missing/declined/expired invitations are refunded, fully satisfied packages receive no money. Clock/debit/ledger/package/counter updates are transactional and survive serverless restarts.
- Additive upgrade20261110-seller-feedback-and-insights creates the new metadata/FKs/indexes and preserves existing rows. Specifically test upgrading an existing NOTNULL UserNotifications.DecisionId while retaining its original FK/receipt; fresh EnsureCreated and the initial-release fixture do not cover this path. Restore the old FK idempotently after a nullable-column upgrade. TestDataSeed derives safe child-first deletion from all new relationships. Browser demo keeps v3 storage/read compatibility. feedback.js is mandatory in Hosting packaging.
